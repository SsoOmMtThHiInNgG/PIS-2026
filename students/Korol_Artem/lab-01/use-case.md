# Use-case: Ивенты «Зафичь, идём?» 🎤

## Первичный актор

Пользователь (участник мероприятия)

---

## Цель

Купить билет на выбранное мероприятие и получить подтверждение участия.

---

## Предусловия

- Пользователь зарегистрирован и авторизован в системе.
- В системе опубликованы актуальные мероприятия.
- Для мероприятия доступны свободные билеты.
- Платёжный сервис доступен для проведения оплаты.
- Пользователь имеет доступ к интернету или мобильному приложению.

---

## Основной поток (Happy Path)

1. Пользователь открывает платформу «Зафичь, идём?».
2. Система отображает список доступных мероприятий.
3. Пользователь выбирает интересующее мероприятие.
4. Система показывает описание мероприятия:
   - название;
   - дату и время;
   - место проведения;
   - расписание;
   - список спикеров;
   - стоимость билетов.
5. Пользователь нажимает кнопку «Купить билет».
6. Система проверяет наличие свободных мест.
7. Система отображает доступные типы билетов:
   - стандартный;
   - VIP;
   - онлайн.
8. Пользователь выбирает тип билета.
9. Система отображает итоговую стоимость заказа.
10. Пользователь вводит данные для оплаты.
11. Система отправляет запрос в Payment Service.
12. Платёжный сервис подтверждает успешную оплату.
13. Система создаёт электронный билет.
14. Информация о билете сохраняется в базе данных.
15. Система отправляет электронный билет на email пользователя.
16. Пользователь получает уведомление об успешной покупке.
17. Use-case завершается успешно.

---

## Постусловия

- Электронный билет создан и сохранён в системе.
- Количество доступных мест на мероприятие уменьшено.
- Пользователь зарегистрирован как участник мероприятия.
- Пользователь получил подтверждение покупки.

---

## Альтернативные потоки

### 7a. Пользователь выбирает VIP-билет

1. Система показывает преимущества VIP-билета:
   - отдельные места;
   - доступ в VIP-зону;
   - дополнительные материалы мероприятия.
2. Пользователь подтверждает выбор.
3. Система пересчитывает стоимость заказа.
4. Поток возвращается к шагу 9 основного сценария.

---

### 9a. Пользователь применяет промокод

1. Пользователь нажимает кнопку «Использовать промокод».
2. Система предлагает ввести код скидки.
3. Пользователь вводит промокод.
4. Система проверяет валидность промокода.
5. Если промокод действителен:
   - система применяет скидку;
   - обновляется итоговая стоимость заказа.
6. Поток возвращается к шагу 10 основного сценария.

---

### 15a. Пользователь хочет добавить мероприятие в избранное

1. Пользователь нажимает кнопку «Добавить в избранное».
2. Система сохраняет мероприятие в профиле пользователя.
3. Система отображает сообщение:
   `"Мероприятие добавлено в избранное"`.

---

## Исключительные ситуации

### 6a. Билеты закончились

1. Система обнаруживает отсутствие свободных мест.
2. Система показывает сообщение:
   `"Свободных билетов больше нет"`.
3. Пользователю предлагается:
   - выбрать другое мероприятие;
   - подписаться на уведомление о появлении мест.
4. Use-case продолжается с шага 2.

---

### 11a. Ошибка платёжного сервиса

1. Payment Service возвращает ошибку или timeout.
2. Система отменяет процесс покупки.
3. Билет не создаётся.
4. Система показывает сообщение:
   `"Ошибка оплаты. Попробуйте позже"`.
5. Use-case завершается неудачей.

---

### 15b. Ошибка email-сервиса

1. Email-сервис не отвечает при отправке электронного билета.
2. Система логирует ошибку.
3. Билет остаётся действительным.
4. Система ставит отправку письма в очередь повторной отправки.
5. Пользователь видит сообщение:
   `"Билет успешно создан. Email будет отправлен позже"`.

---

### 1a. Пользователь не авторизован

1. Пользователь пытается купить билет без входа в систему.
2. Система перенаправляет пользователя на страницу авторизации.
3. После успешного входа пользователь возвращается к покупке билета.

---

## Бизнес-правила

- Один пользователь может купить несколько билетов только при наличии свободных мест.
- Один билет имеет уникальный QR-код.
- После успешной оплаты билет не может быть удалён без возврата средств.
- Пользователь не может купить билет на уже завершённое мероприятие.
- Все операции оплаты должны логироваться.

---

## Нефункциональные требования

- Время ответа системы при покупке билета не должно превышать 5 секунд.
- Система должна поддерживать одновременную покупку билетов несколькими пользователями.
- Email-уведомление должно отправляться максимум в течение 1 минуты после покупки.
- Все пользовательские данные должны передаваться по HTTPS.

---

## Итог

Данный use-case описывает процесс покупки билета на мероприятие в системе «Зафичь, идём?» 🎤 с учётом основного сценария, альтернативных потоков и возможных ошибок. Сценарий охватывает взаимодействие пользователя с системой, платёжным сервисом и сервисом уведомлений.
